# 管理批量操作与验收

本轮范围为用户启停用、商品审核、帖子审核、任务发布审核。已按负责人答复实现逐条独立处理，成功保留，失败列出。接口字段、权限和恢复语义见[批量接口补充](../api/管理批量操作接口补充.md)。

|层次|实际变更|目的|
|---|---|---|
|数据库|V007新增admin_batch_jobs和admin_batch_items|保存原请求身份摘要、规范化动作及每条结果，避免刷新或重启丢失批次|
|服务端|AdminBatchService及Controller|持久接收、幂等重放、本人查询、逐条事务和worker恢复|
|业务校验|直接调用AccountService.status、productAction、postAction和publication|继续执行原权限、审计、状态冲突、积分与现金限制|
|共用前端|AdminBatchActions及useAdminSelection|统一勾选、确认、原因、结果与失败项重试，不复制四套组件|
|现有页面|用户、商品、帖子、任务表增加当前页勾选|查询、翻页和重新加载清空选择，审核后刷新真实列表|

进入用户管理、交易管理、内容发布管理的商品/帖子页，或悬赏任务列表即可验收。用户列表不允许勾选本人；审核列表只允许勾选待审核记录，提交时服务端仍检查最新状态。共用结果区显示逐条成功或失败原因，最近批次可查询当前账号近10次结果，切换页面后重新读取数据库。

## 本地运行与恢复

1. 按原本地账号、文件、任务、通知与售后工具完成V001–V006，使用现有独立库。运行 `scripts/local_admin_batch_db.py` 仅执行V007；脚本校验33320端口、schema及实际datadir，拒绝部分DDL盲目重跑。
2. Java17构建并启动已打包服务，沿用私有配置，增加 `--campus.admin-batches.worker-enabled=true`。保留通知worker配置；现金开关保持false。
3. 关闭批量worker只会暂停待执行项，提交及查询仍可用；重新开启后继续处理。应用回退前先停入口与worker，保留两张表、已有审计和单条幂等数据，不删表或重建初始库。
4. V007编号须G登记后才可用于共享环境。本次仅升级独立本地库，不代表远程部署、真实付款或全后台功能完成。

## 验证方法与证据

- `scripts/check_admin_batches_http.py`：真实HTTP及MySQL，验证四类批量、部分成功、缺失ID/冲突、本人保护、失效会话、权限、同key并发、响应丢失、积分只释放一次。临时数据库触发器让“保存成功结果”失败，确认原业务状态、审计和幂等记录全部回滚，而下一项仍能成功。
- 重启验证：在worker关闭的真实进程运行上项脚本 `--prepare-restart`，重启Java并开启worker，再运行 `--verify-restart`。验证持久待执行批次恢复，另两个提交者会话撤销/角色降级的批次不能越权执行。脚本不会自动重启用户服务。
- `scripts/check_admin_batches_browser.cjs`：先运行HTTP脚本生成新夹具，再操作实际打包UI及接口，包含外部单条审核抢先变更导致的真实部分失败、仅失败项重试确认、四页操作、过滤清空勾选、历史结果、公共布局实例及900px防溢出检查。不拦截或伪造业务响应。
- 原单条内容/任务、账号、公共布局和分析页按本轮验证记录回归。所有合成账号、商品、帖子和任务均由脚本明确标记；SQL任务夹具不是用户发布API实现。

机器结果和截图保存在被Git忽略的 `.local/auth-dev/admin-batches/`。实际测试结果以其中本轮PASS记录为准，未通过的中间记录不作为完成证据。
